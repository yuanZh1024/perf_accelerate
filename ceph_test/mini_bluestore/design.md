# Mini BlueStore 设计文档

版本 v1.0 | 2026-11-16 | 性质：学习型原型，用于理解 BlueStore 的核心设计，不用于生产

## 1. 背景与目标

BlueStore 是 Ceph OSD 的存储后端：不经过文件系统，直接管理裸块设备，用 KV 数据库（RocksDB）记录元数据。本项目用 C 实现一个最小版本，把它的骨架复现一遍。

**目标**

- 直接管理裸块设备（如 /dev/sde），不经过文件系统
- 对象级读写：按对象名存取一段二进制数据
- 崩溃一致性：任意时刻进程崩溃，重启后对象要么是完整的旧版本，要么是完整的新版本
- 静默损坏检测：读取时校验数据，发现盘上数据被悄悄改坏

**非目标**

多线程并发、异步 IO、压缩、多副本与自动修复、对象分片与多 extent、性能优化。

## 2. 总体架构

```
              调用方（测试程序 / 上层）
                      │  store_write / store_read / store_delete
                      ▼
            ┌───────────────────────┐
            │  Store（编排层）       │  串联各模块，决定操作顺序与崩溃语义
            └──┬───────┬────────┬───┘
               │       │        │
               ▼       ▼        ▼
          ┌────────┐ ┌────────┐ ┌────────┐   ┌─────────┐
          │ Alloc  │ │  Meta  │ │  Disk  │   │ crc32c  │
          │ 位图    │ │RocksDB │ │ 裸盘IO │   │ 校验算法 │
          └────────┘ └────────┘ └────────┘   └─────────┘
            内存      普通目录     /dev/sde      纯函数
```

说明：为简化，RocksDB 放在普通文件系统目录里（真实 BlueStore 里它跑在自己的 BlueFS 上）；对象数据仍然全部在裸盘上。

**三条核心设计原则**

1. **元数据是唯一真相。** 对象存不存在、数据在哪，只看元数据里有没有记录，不看数据块里有没有内容。
2. **数据先于元数据落盘。** 元数据提交时，它所指向的数据必须已经完整落盘。
3. **不原地覆盖。** 覆盖写一律写到新位置，提交新元数据之后才释放旧空间（写时复制）。

## 3. 模块职责

### 3.1 Disk（磁盘层）

**职责：** 提供按块号读写裸盘的能力，并把 O\_DIRECT 的对齐要求隐藏在内部。

| 接口                             | 说明                                                         |
| -------------------------------- | ------------------------------------------------------------ |
| disk\_open(path)                 | 以 O\_RDWR、O\_DIRECT、O\_SYNC 打开设备，申请 4 KB 对齐的缓冲区 |
| disk\_write\_block(n, data, len) | 写第 n 块，不足一块的部分补零；返回即已落盘                  |
| disk\_read\_block(n, out)        | 读第 n 块（整块 4 KB）                                       |
| disk\_close()                    | 释放资源                                                     |

**设计要点**

- 绕过页缓存（O\_DIRECT）：写成功就意味着数据真的到了盘，崩溃一致性依赖这一点
- 位置、长度、内存缓冲区地址都必须 4 KB 对齐，所以接口只提供整块读写
- 内部共用一个缓冲区，非线程安全

**不负责：** 不知道什么是对象；不知道某一块有没有被占用；不做校验。

### 3.2 Allocator（分配器）

**职责：** 管理盘上空间的使用状态，回答「新数据可以放在哪」。

| 接口                            | 说明                                                         |
| ------------------------------- | ------------------------------------------------------------ |
| alloc\_init(total\_blocks)      | 创建位图，全部空闲                                           |
| alloc\_alloc(count)             | 找 count 个连续空闲块，标记为已用，返回起始块号；找不到返回 -1 |
| alloc\_free(start, count)       | 把一段块标记为空闲                                           |
| alloc\_mark\_used(start, count) | 直接标记已用（预留块 0、重启恢复时使用）                     |

**设计要点**

- 位图：每个块 1 bit，0 表示未分配，1 表示已分配。2 GB 盘共 524288 块，位图仅 64 KB
- 策略 first-fit：从头扫描，用一个计数器记录当前连续空闲长度，够长就取。简单，但会产生碎片
- 分配结果是一个 extent：（起始块号，块数）。起始块号乘以 4096 就是盘上的字节偏移
- **位图只在内存里，不持久化。** 它是元数据的派生物，重启时由元数据重建

**不负责：** 不读写盘；不知道这些块属于哪个对象；不保证分配出去的空间最终被使用（调用方负责归还）。

### 3.3 Meta（元数据层）

**职责：** 持久化「对象名 → 数据位置」，并提供原子提交。

| 接口                        | 说明                                                   |
| --------------------------- | ------------------------------------------------------ |
| meta\_open(dir)             | 打开或创建 RocksDB，写选项 sync=1                      |
| meta\_put(name, onode)      | 同步写入一条 onode；返回成功即已落盘，要么完整要么没有 |
| meta\_get(name, onode)      | 0 找到，1 不存在，-1 出错；成功后需调用 onode\_free    |
| meta\_delete(name)          | 同步删除                                               |
| meta\_rebuild\_alloc(alloc) | 遍历所有 onode，把它们占用的块在位图里标记为已用       |

**设计要点**

- 元数据的写入就是整个系统的**提交点**：RocksDB 先写 WAL 再返回，sync=1 保证 WAL 已刷盘
- 一个对象一条 KV 记录，key 是对象名，value 是二进制 onode（格式见第 4 节）

**不负责：** 不接触数据块；不做空间分配；不判断数据是否完整（校验在读路径做）。

### 3.4 crc32c（校验算法）

**职责：** 纯函数，对一段内存计算 crc32c（Castagnoli 多项式 0x82F63B78，查表实现）。自检用例：对字符串 123456789 计算，结果应为 0xE3069283。

### 3.5 Store（编排层）

**职责：** 对外提供对象接口，决定各模块的调用顺序，处理失败回滚，并在启动时完成恢复。顺序与回滚规则是本项目设计的核心，见第 5 至 8 节。

| 接口                                | 说明                         |
| ----------------------------------- | ---------------------------- |
| store\_open(dev, meta\_dir)         | 打开磁盘与元数据，重建分配器 |
| store\_write(name, data, len)       | 写对象（新建或整体覆盖）     |
| store\_read(name, out, cap, outlen) | 读对象并校验                 |
| store\_delete(name)                 | 删除对象                     |
| store\_close()                      | 关闭                         |

## 4. 数据布局与数据结构

**盘布局**

```
块号:   0      1 ......................................... N-1
      [预留]  [ 对象数据区：由分配器按块分配 ]
```

块 0 预留，将来可放超级块（魔数、版本、设备信息）。其余块都是对象数据区。

**Onode（元数据记录）**

| 字段     | 类型             | 含义              |
| -------- | ---------------- | ----------------- |
| start    | uint64           | 数据起始块号      |
| nblocks  | uint64           | 占用块数          |
| size     | uint64           | 对象真实字节数    |
| crcs\[\] | uint32 × nblocks | 每个块一个 crc32c |

RocksDB 中的存储格式：key 为对象名；value 为 24 字节头部（start、nblocks、size）加上 nblocks 个 4 字节的 crc，总长度 24 + 4 × nblocks。读取时会校验该长度，不符视为元数据损坏。

**size 与 nblocks 的关系：** nblocks 等于 size 向上取整到 4096 的块数。末尾那个块不足的部分补零，crc 是对补零后的整块计算的，所以读取时可以直接对盘上读出的整块校验，最后按 size 截断。

**简化约定：** 一个对象只对应一个连续 extent，不支持部分覆盖或追加，写入总是整对象替换。

## 5. 写入流程

### 5.1 步骤

以下为 store\_write(name, data, len) 的完整流程：

0. **查旧版本。** 若对象已存在，取出旧 onode（用于最后释放旧空间）。
1. **调用 Allocator 申请空间。** 计算所需块数，调用 alloc\_alloc，位图中对应块由「未分配」变为「已分配」。申请失败（空间不足或碎片）则直接返回错误，此时没有任何副作用。
2. **得到起始块号。** 起始块号乘以 4096 就是写入偏移。此时只有内存位图变了，盘和元数据都没动。
3. **调用 Disk 逐块写数据。** 对第 i 个块：取 4 KB 数据（不足补零）→ 计算 crc32c 并记录 → disk\_write\_block(start + i)。全部写完意味着数据已全部落盘。若任一块写失败，立即归还空间并返回错误。
4. **调用 Meta 提交元数据。** 把（start、nblocks、size、crcs）作为 onode 同步写入 RocksDB。**这一步是提交点：** 返回成功之后，新版本才算存在。
5. **元数据写失败的处理。** 此时数据已写在盘上，但没有任何元数据指向它，是垃圾数据。处理方式：alloc\_free 归还这段空间，返回错误。旧版本（如果有）仍然完好有效。
6. **提交成功后释放旧空间。** 若是覆盖写，把旧 extent 归还分配器。

### 5.2 时序图

```
Store            Allocator        Disk                Meta(RocksDB)
  │ alloc(n)         │              │                     │
  │─────────────────►│              │                     │
  │◄───── start ─────│              │                     │
  │ 逐块: 补零 + crc32c             │                     │
  │ write_block(start+i) ───────────►│  落盘               │
  │ ……（重复 n 次）                  │                     │
  │ put(name, onode{start,n,size,crcs}) ─────────────────►│
  │◄──────────────────── 提交点：返回即已落盘 ────────────│
  │ free(旧 extent)  │              │                     │
  │─────────────────►│              │                     │
```

### 5.3 为什么是这个顺序

| 设计决定               | 理由                                                         |
| ---------------------- | ------------------------------------------------------------ |
| 先写数据，后提交元数据 | 元数据一旦可见，它指向的数据必须已经完整。反过来的话，崩溃后会出现账上有记录、数据却不完整的状态 |
| 写到新位置，不原地覆盖 | 原地覆盖写到一半断电，旧数据已毁、新数据不全，两头落空。写时复制让旧版本在提交前始终完好 |
| 提交之后才释放旧空间   | 若先释放旧空间，提交前崩溃，旧元数据会指向已释放甚至被复用的空间 |
| 不需要额外的 journal   | 原子性来自「新位置 + 一次元数据提交」，数据只写一遍，这也是 BlueStore 相对 FileStore 的核心改进 |

### 5.4 失败与崩溃处理总表

| 发生位置                             | 此时的状态               | 处理                                         | 对象最终状态 |
| ------------------------------------ | ------------------------ | -------------------------------------------- | ------------ |
| 步骤 1 分配失败                      | 无副作用                 | 返回 -1                                      | 不变         |
| 步骤 3 某块写失败                    | 部分块已写               | alloc\_free，返回 -1                         | 旧版本       |
| 步骤 4 元数据写失败                  | 数据完整但无人认领       | alloc\_free，返回 -1                         | 旧版本       |
| 进程崩溃，提交点之前                 | 盘上有孤儿数据           | 重启时重建位图，孤儿块自然空闲               | 旧版本       |
| 进程崩溃，提交点之后、释放旧空间之前 | 新版本已生效，旧块未归还 | 重启重建位图，旧块不属于任何 onode，自然空闲 | 新版本       |

## 6. 读取流程

1. Meta 查询对象，不存在则返回 1
2. 检查调用方缓冲区是否够大，不够返回 -2
3. 对每个块：Disk 读出整块 → 重新计算 crc32c → 与 onode 中记录的值比较。不一致说明盘上数据已被悄悄改坏，输出日志（对象名、块号）并返回 -3，**不返回坏数据**
4. 按 size 截断拷贝，去掉末尾补零

**设计要点：** crc 存在元数据里，而不是和数据放在同一个块旁边。这样即使写偏位置或整块丢失，数据和 crc 也不会一起错，两边能互相对账。校验只负责发现，不负责修复；在真实 Ceph 中，发现错误后由上层从其他副本修复。

## 7. 删除流程

1. Meta 删除记录（提交点）
2. 提交成功后，Allocator 释放对应空间

**顺序理由：** 若先释放空间再删元数据，在两步之间崩溃会留下元数据指向已释放空间的悬空引用，该空间一旦被新对象占用，读旧对象就会读到别人的数据。先删元数据则最坏情况只是空间暂时没归还，重启后会自动回收。

## 8. 崩溃一致性与恢复

### 8.1 启动恢复流程（store\_open）

1. 打开裸盘，通过 lseek 到末尾得到设备大小，算出总块数
2. 创建全空闲的位图，预留块 0
3. 打开 RocksDB（自动重放 WAL，恢复到最后一次成功提交的状态）
4. 遍历全部 onode，把它们占用的块在位图中标记为已用

恢复后，位图等于块 0 加上所有 onode 的 extent。凡是没有被元数据认领的块，不论是崩溃遗留的孤儿，还是未归还的旧空间，都自动视为空闲，**不需要单独的垃圾回收流程**。这正是「分配器不持久化」这个设计的收益。

### 8.2 一致性不变量

| 编号 | 不变量                                                   | 由谁保证                   |
| ---- | -------------------------------------------------------- | -------------------------- |
| I1   | 每个 onode 指向的所有块都已完整落盘，且 crc 与元数据一致 | 写入顺序（先数据后元数据） |
| I2   | 任意两个 onode 的 extent 不重叠                          | 分配器；重启后由重建保证   |
| I3   | 位图 = 块 0 ∪ 所有 onode 的 extent                       | 启动时重建                 |

### 8.3 崩溃注入测试

在覆盖写流程中设置 4 个崩溃点，用 \_exit(42) 让进程立刻终止，然后由新进程重新打开存储并检查（旧版本为 3 块的 A，新版本为 5 块的 B）：

| 崩溃点 | 时刻                           | 预期重启后                 |
| ------ | ------------------------------ | -------------------------- |
| 1      | 分配之后、写数据之前           | 完整旧版本，空闲块数无泄漏 |
| 2      | 只写了新数据的第 1 块          | 完整旧版本，空闲块数无泄漏 |
| 3      | 数据全部写完、元数据提交之前   | 完整旧版本，空闲块数无泄漏 |
| 4      | 元数据提交之后、释放旧空间之前 | 完整新版本，空闲块数无泄漏 |

另有一个不崩溃的对照组。分界线就是元数据提交点：提交之前死，对象是旧的；提交之后死，对象是新的。每个场景检查三项：内容完整且无半新半旧、校验通过、空闲块数与期望一致。

**测试边界：** \_exit 模拟的是进程崩溃，不是断电。由于盘以 O\_DIRECT 和 O\_SYNC 打开，写返回时数据已到盘，所以能有效验证写入顺序是否正确；但覆盖不到盘自带写缓存丢失、撕裂写等硬件层问题。

## 9. 错误码约定

| 函数          | 返回值                                                       |
| ------------- | ------------------------------------------------------------ |
| store\_write  | 0 成功；-1 失败（空间不足、IO 错误、元数据写失败，失败时已回收空间，旧版本不受影响） |
| store\_read   | 0 成功；1 对象不存在；-1 IO 或元数据错误；-2 调用方缓冲区太小；-3 校验和不匹配 |
| store\_delete | 0 成功；-1 对象不存在或元数据错误                            |

## 10. 与真实 BlueStore 的对照

| 方面       | 本实现                              | 真实 BlueStore                                               |
| ---------- | ----------------------------------- | ------------------------------------------------------------ |
| 设备访问   | pwrite 加 O\_DIRECT，同步           | KernelDevice，使用 libaio 或 io\_uring 异步 IO，也可选 SPDK  |
| 分配器     | 位图 first-fit，一个对象一个 extent | 多种分配器实现，一个对象可由多个 extent 组成                 |
| 元数据存储 | RocksDB 放在普通目录                | RocksDB 跑在 BlueFS 上，可放到独立的 SSD 或 NVMe             |
| 元数据结构 | 每对象一条简单 onode                | onode 内含 extent map、blob 等更复杂的结构                   |
| 校验和     | 每 4 KB 块一个 crc32c               | 默认 crc32c，粒度与算法可配置                                |
| 崩溃一致性 | 新位置写入加元数据原子提交          | 同样的核心思路，小写额外走 deferred write（先进 RocksDB 的 WAL） |
| 多项更新   | 一次只改一条 onode                  | 用 RocksDB WriteBatch 把多项元数据更新打包成一次原子提交     |
| 并发       | 单线程                              | 多线程、事务状态机                                           |
| 压缩       | 无                                  | 可选                                                         |
| 损坏修复   | 仅报错                              | 返回 IO 错误，上层 OSD 从副本修复                            |

## 11. 已知限制与后续改进

**已知限制**

- **元数据提交结果可能不确定。** 当前把 meta\_put 返回错误视为「未提交」并回收空间。严格来说，错误返回（例如超时）时提交可能其实已经生效，此时回收空间会导致元数据指向已释放的块。当前实现未处理这种情况
- **没有超级块。** 设备大小每次由 lseek 推出，没有魔数、版本、设备标识，无法防止误用别的盘，也无法检测盘被替换
- **单 extent。** 碎片严重时，即使总空闲块数足够，大对象也可能分配失败
- **只支持整对象写。** 不支持部分覆盖和追加
- **单线程。** 没有锁，Disk 共用一个缓冲区
- **重启重建需要扫描全部 onode。** 对象很多时启动变慢
- **校验仅检测不修复**
- **元数据格式没有版本号。** 格式变更需要清库（开发过程中已发生过一次）
- **未覆盖硬件层故障。** 依赖 O\_SYNC，不处理写缓存丢失与撕裂写

**后续演进方向（按学习价值排序）**

1. 引入超级块：魔数、版本、设备大小、元数据格式版本
2. 用 RocksDB WriteBatch 把多项更新合并为一次原子提交
3. 支持多 extent，缓解碎片问题
4. 小写走 deferred write（先写 WAL，再异步落到数据区），体会它与大写路径的区别
5. 异步 IO（libaio 或 io\_uring）
6. 到真实 Ceph 测试集群的 OSD 上，对照本文第 10 节观察设备布局与元数据
